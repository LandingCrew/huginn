# Doc 9 implementation map: what to build, what to prune

**Status:** plan, 2026-10-08. Nothing here is built. Merged from six read-only passes over the code, one per part of the redesign (scoring and context, learner and persistence, item description, state and sensors, slots and wildcards, tooling and config), with the claims that change the plan spot-checked against the source. A fresh-context verifier then tried to invalidate it (2026-10-08); its corrections are applied.

The target is the model in [doc 9](9-context-as-learner-input.md): `score = Σ θ·need·cap + b`, a conditional logit over the page with an outside option, a diagonal-Gaussian belief per weight, the Bayesian challenger rule and uncertainty-ranked wildcards.

**Size:** roughly 7–8k lines are pruned or replaced, most of it in the classifiers (~2,600), the context rules (~1,200), the multipliers and prior (~1,000) and the per-type dumps (~950). Counts are approximate, from the passes.

## Phases

Each phase lists what it builds and what it may prune. A phase only prunes what nothing later still reads.

- **Reuse:** move `AvName`, `KeywordList`, `PluginOf`, `CsvQuote` from `ConsoleCommands.cpp` into `src/util/FormRead.h`; take the MagicEffect helpers from `SpellClassifier.cpp` (`GetCostliestEffect` 1182, `ResistedElement` 1299, `DetermineMagicSchool` 1279, cloak/hazard resolution 310-621), keyword checks from `ItemClassifier.cpp`, weapon stat reads from `WeaponClassifier.cpp:241-431`, player enchantments from `WeaponRegistry.cpp:876-889` and `ApparelRegistry.cpp:226-254`.
- **Split cap into static and runtime.** Static columns go in the catalog. `weapon_charge`, `overshoot_*`, `stack_count`, `ammo_matches_launcher`, `school_fortified` are computed per tick (new `src/learning/CrossFeatures.*`). Tempered and player-enchanted weapons need a per-instance cap.
- **Candidates carry a catalog index**, not 243 floats (`CandidateTypes.h:382` asserts ≤ 56 bytes).
- **Armour menu picks must reach the learner.** `ExternalEquipListener.h:81-98` drops every armour equip made outside Huginn (its comment: most of it is ordinary dressing, and turning it on shifts accept%). With all carried armour a candidate and the menu a choice set, lift it; record the accept% shift in the soak baseline. *Decided by the user 2026-10-08: lift the skip* (the lift itself is R2 work).
- **`hg dump all` becomes a view of the catalog** and absorbs the eight dump gaps in doc 9. Check coverage against `9-data/effects.csv`.
- Prunes nothing yet.

**As built (R2, 0.23.12), where it differs from the plan above:**
- The rules live in `src/core/` (`EffectRules`, `EffectMapper`, `EffectColumns.h` generated from effects.csv, and `MiniRegex`: std::regex has no lookbehind and is slow in Debug) and are ported from the Python reference extractor that measured doc 9's coverage (`tools/effects/reference/`), not from the classifiers; `SpellClassifier`/`ItemClassifier`/`WeaponClassifier` code was not reused. The game side (`src/effect/`) only reads forms.
- The per-load-order override (layer 2) is checked **first**, before the keyword table, so an entry can correct a keyword misroute; it is an optional `Huginn_EffectOverrides.ini` (none ships yet).
- The catalog reads the forms when the main menu first opens (a main-thread task queued then), not in Huginn's kDataLoaded handler: SKSE hands kDataLoaded to plugins in turn, and keyword distributors (KID, SPID) that run after Huginn add keywords the rules read (LoreRim's `DBWR_Silver*`). A task queued from kDataLoaded is no promise of "later" (SKSE may run tasks added during its pass in the same pass). kNewGame/kPostLoadGame build too, as a fallback for a setup that skips the main menu (a no-op once built). The mapping runs on a worker thread (seconds in Debug on LoreRim). Since 0.23.47 the read is sliced: in one go it held the main thread 3.1-3.25 s at the main menu on LoreRim (Tracy, 2026-10-16/17); now it reads in 12 ms slices (4 ms in 0.23.47; at 4 ms a LoreRim main menu read only ~1.2 of the 3.2 s before the player loaded, 2026-10-28), one SKSE task per frame queued from the Present hook (so a task pass cannot chain two), every form still on the main thread in the same order (`core/SlicedWalk.h`, host-tested against an unsliced walk). What is left when a game starts loading is read at once at kPreLoadGame (kNewGame for a new game), before the save touches a form.
- The cross-features are `src/core/CrossFeatures.h` + `src/effect/CrossFeatures.*` (not `src/learning/`), wired only as far as `hg cap`: nothing computes them per tick while nothing reads them. R4 is the first per-tick reader.
- Candidates do not carry a catalog index yet (it would change `CandidateTypes`, and R2 changes no scores); the catalog is keyed by FormID. Do it with R4.
- The armour items (all carried armour a candidate; the `ExternalEquipListener` armour skip) are split into their own PR: they change candidates and accept%.
- A Cloak/hazard is damage itself only by a MagicDamage* keyword; otherwise it maps through its payload spell, with no payload by its own description, and with neither it is left out of coverage like a helper.
- A graded column with magnitude 0 has an unknown strength. On a script route (keyword, name, description, override) it is the neutral value 0.5 (times D where the rule has one), never the top; presence-only columns stay 1. Through the engine's data (route Data) an unknown strength (magnitude 0; a Light with no light radius) is resolved from the effect's own text: a description that hits a no-column rule is counted unmapped ("Restoration spells are 25% more powerful"); a description that names a column keeps the row under that column, with its stated number as the magnitude, or a stated percentage as the value p/100 outside the population (Dragonhide's "ignores <80>%" is 0.8 -- percentages and points never share a population), or with no number the neutral value 0.5; a name of the same family keeps it at 0.5; a visible row with no description beside a row the item keeps is a carrier, dropped and not counted (Requiem's Dispel Armor, the Mystic/Dread variants beside Bound Armor); anything else is counted unmapped (Instant Kill, Soul Gem Evocation, Wabbajack). `huginn_effect_report --carriers-out` lists every carrier and prints coverage both ways. A Light effect grades its associated light's radius. A row of unknown strength (0.5) counts for its column only when the item has no row of known strength there, and is the item's primary row (delivery, timing, school) only when it keeps no known row. Percentages valued as p/100 on a points column (defense_armor) are an approximation that ranks them.
- Known mapping issues for the R6 data review (pre-existing, not R2 regressions; left as they are): Wind Knockup -> utility_unlock; "unlocks the seal" / "new facets" -> utility_unlock; Windwalker's immunity to knockdown -> control_stagger; the Thieves Guild Gloves' poison-resistance reduction -> resist_poison; Frostmoon Howl and Holy Aura -> damage by name; Control Weather -> influence_command; Soul Split, Power of the Master, Dark Sacrifice and Necromancer's Ritual -> summon_reanimate.
- The catalog is built once, after keyword distributors; game data changed at runtime after a save loads (a Papyrus AddKeywordToForm, SetNthEffectMagnitude, an effect a script adds) is not seen. The LoreRim gate found one such item: Waterskin.esp's "Waterskin (Full)" gains a "Restore Hunger Very Small" row after load.
- Tempering adds (h - 1) x 10 damage (the registry's measured model), it does not multiply.
- **Side effects (0.23.16, from the LoreRim R3 session).** A harm row (damage, drain, weaken regen, weakness, weaken combat, control, influence, absorb, drain skill) on a food or potion that is detrimental or hostile is the drinker's side effect: a vital's damage or drain sets `self_harm_<vital>` (an Amount, graded in its own population), anything else the family `self_harm` (P); never the target-harm column, which a learned weight pays for poisons and weapons (LoreRim raw food's Weak Stomach read as `damage_stamina`). The only item-level rule: applied per row in `MapItem`, `ClassifyEffect` keeps the MGEF's own column. Such a row -- like any row of a food or potion that harms the user, whatever column it keeps (survival_intoxication's "Drugged") -- does not set `hostile`, and a self_harm row is the primary row only when the item keeps nothing else. Poisons and spells are untouched, and so are a Cloak/hazard's payload rows and a wrapper's own description: they hit the actors around the user (no food or potion carries one in the three dumps). 239 -> 243 columns. Rows moved: vanilla+ 29, Simonrim 13, LoreRim 196 (85 `self_harm_stamina`, 13 magicka, 12 health, 86 the family); coverage unchanged (only mapped rows move).

### Phase 2: describe situations (need vector)

- **New:** `NeedId`/`NeedVector` generated from `needs.csv`; `ResponseCurve` (linear, quadratic, logistic, logit, gaussian, step); a `[Needs]` INI section for curve parameters.
- **Sensors to add or fix:** encumbrance ratio (kept as a float, polled at 1 Hz), a decaying damage rate per element, combat-onset/ended and submerged timers on `steady_clock`, a held multi-hot target-family bitmask (union of the living combat hostiles, held until combat ends; no line-of-sight logic), target summoned / casting element / archer from the hostile loop, restore-pending from the active-effect walk, drop ahead (raycast; API unconfirmed).
- **Compute the vector once in `GatherState`** (`PipelineCoordinator.cpp:143-150`) as a pure function of the snapshots, and cache it; reset new timers in `ResetTrackingState`.
- **Need-signature skip gate:** a quantised (0.05) signature, so continuous needs re-score. It replaces `ambientSignature`, the elemental window and, later, the GameState buckets.
- Rules stay as they are: the vector is computed and logged only.
- **As built (R3, 0.23.14).**
  - **The definition is the csv.** `needs.csv` gained `curve_kind`, `curve_p1`, `curve_p2` (each need's default curve, read off the prose `curve` column; where the csv gives only a centre, the slope is a designer default) and `r3_input` (the curve's input as a formula over the snapshot's fields). `tools/needs/make_need_ids.py` generates `core/NeedIds.h` and the `[Needs]` block of `configs/Huginn.ini`; `NeedIdsTests` fails on drift.   - **Drop ahead** (`state/DropAheadProbe`, `core/DropAhead.h` `ProbeAll`). Three points at 70/175/280 units along the movement (>= 20 units/s, else the facing). Each is first reached by two horizontal picks from the previous point (the player for the first), at waist (64) and knee (24) height above the PREVIOUS point's ground (the player's feet, then each reached point's down-ray hit), so the picks climb a walkable slope (round 3: from the feet alone, probe 3 went unknown above ~5 degrees). ANY hit on the waist pick blocks, whatever its layer (a wall, a door, an invisible wall or collision box at an edge, a slope steeper than ~42 degrees). A hit on the knee pick is told apart by the down ray at the point: ground there at or above the knee height is rising ground or a step up (known); lower ground or a void behind is a parapet or low wall (blocked). The first blocked point and every one beyond it are unknown. Then a ray 16000 units down from the point at waist height above the previous ground (0.23.22; the 4000 before it ended above the sea under a LoreRim cliff 5474 high, so a sea landing read as a void; `DropProbeConfig::rayLength` gives the reasoning, and that whether the length costs time is not measured): a hit on ground (static, anim static, transparent, trees, props, terrain, ground) is the surface; actors and clutter are cast through from just past the hit, at most 8 times (`kMaxRecasts`), and running out makes that one point unknown; no hit at all is a real void (a very big drop: down to the ray's bottom, 16000 under its start, so 15936 from flat ground; water known only below the ray's bottom does not change that, it stays depth 0). All unknown = -1, "not measured". The sequence is core code over an injected ray cast and host-tested (parapet, invisible wall, uphill, stairs, a crowd, which point becomes unknown, walkable slopes of 5-30 degrees, a 6-degree rise to a crest with a cliff behind, a step up). Ray filter: layer `kLOS` in the player's own collision group (its bodies never block). Water: `TESObjectCELL::GetWaterHeight` at each reached point, from the cell the point lies in (0.23.19 fix round; see Known limits), at the point's XY and its down ray's real start Z. The down ray passes through water to the bed, so the depth is the surface down to the hit (to the ray's bottom with no hit; the bottom follows the ray's real start, waist height above the previous point's ground). Since 0.23.19 (`MeasureAhead`) a landing in water at least `kSafeLandingDepth` (128 units, a guess: the game's threshold is not known) deep is no drop, since Skyrim takes no fall damage there, and shallower water is measured to its surface; the same pass gives `deep_water_ahead`, the deepest water over the known points (-1 with none known, so 0 while swimming, when the probe is skipped).
  - **Edge needs** (0.23.50, `core/EdgeApproach.h`, fed by the same probe pass). `time_to_edge`: the distance along the probe direction to the nearest known probe point whose drop is at least drop_ahead's centre (466), over the horizontal speed toward it in units per GAME second; NEVER standing, backing off or with no edge (coarse: 70/175/280). `edge_approach`: the least-squares slope, over the last 1.5 game seconds, of each pass's proximity (the drop_ahead curve averaged over the three points, unknown 0); the window restarts on a load, a change of interior cell or worldspace, a teleport, every probe skip and a turn of the probe direction past 45 degrees. Both logged only; curves chosen, not fitted (needs.csv).

The rays are cast from a vtable hook on `PlayerCharacter::Update` (index 0xAD, installed in `SKSEPlugin_Load`), called from the game's main update -- the place prior art casts camera rays from (SkyrimCameraDisocclusion). Throttled to every 100 ms; on at kPostLoadGame / kNewGame, off at kPreLoadGame and when the main menu opens (quit to the main menu leaves the player singleton alive); skipped while a LoadingMenu is open, without player 3D, a parent cell, an attached cell or a physics world, and while airborne, swimming or mounted. The world is held by an NiPointer and read under `bhkWorld::worldLock` (BSReadLockGuard). A position jump past 500 units between two probes is a teleport: the heading comes from the facing (round 3 saw the old-to-new delta used after a coc). Anything the probe throws is caught and logged once; the game's update has already run, first. The sensor reads the last reading (older than 1 s: not measured). Since 0.23.16 that age counts unpaused time only (`Core::Needs::ReadingAge`): the hook does not run while the game is paused (the console, a menu) but the update loop keeps polling, so a wall-clock age read "not measured" one second into every menu; kPreLoadGame, kPostLoadGame/kNewGame and the main menu clear the reading, so a paused age never carries one into another session. `hg needs` prints the reading's age.   - **Known limits, not fixed (rounds 2 and 3):** an obstacle open between the knee and the waist (a railing with a gap there) is not seen, so a void behind it reads as a cliff; the water height came from the player's cell, so a river across a cell border could be missed -- and since 0.23.19, when water at least `kSafeLandingDepth` deep cancels a drop, a lake cell's surface read over the next, lower, dry cell would have zeroed a real cliff (a false negative for `drop_ahead`, a false positive for `deep_water_ahead`). ## Decisions (the user, 2026-10-08)

- [x] **"Nothing pressed" is recorded when a need expires.** One record per need episode that resets with no press, with the page at the onset. It feeds u0 and opportunity counting.
- [x] **u0 depends on the situation:** an outside-option effect column, θ[need, out], learned like any other weight. Needs that never fire keep their starting value.
- [x] **Co-picks are processed in sequence** (Plackett–Luce). The user's reading: co-picks and sequential picks covary, and processing them in order keeps that out of the update.
- [x] **The page set includes everything visible:** wildcard, override and Remembrance slots too (P5 needs the choice set as shown). This reverses today's exclusion at `EquipSubscribers.h:69`.
- [x] **The menu is a second choice set** at a learned cost κ (theory page, P11). A menu pick teaches the item picked through its need × effect pairs; κ settles at the observed reach-in rate. The favorites-always-pass rule (`UtilityScorer.cpp:98-110`) goes: menu picks carry that evidence now. Today a menu pick already trains the item's own vector (`ExternalEquipLearner.cpp:67` → `SelectionTracker::Select`); what was missing is the need and effect attribution.
- [x] **All carried armour is gear and enters the candidate pool; gear in combat is left to the learner, not a hard rule.** Mid-fight swaps (gloves of Destruction ↔ gloves of Two-Handed) are free in the engine today; they are not expected to recur often, so the data per armour item will be thin, and b and the shared θ carry it. A future swap cost becomes a feature or part of κ_move. Lift `ApparelClassifier`'s scope guard (`ApparelClassifier.h:11-17`).
- [x] **Powers stay out; a bonus only if the system works very well.** Mods use powers as a grab bag (debug tools, Weathersense, prayers for favour), players keep them on the favourites list, and their context is harder to judge than spells'. Shouts are skipped too (the user, 2026-10-08).
- [x] **Target type keeps the combat-hostile union, no line-of-sight logic.** The engine's combat state is all or nothing, the crosshair sees one actor while the player sees several in frame, and manual tagging per fight is not reasonable.
- [x] **Coverage loss is not a blocker.** Script-only spells were a back-of-the-envelope concern; unmapped items still get b. Run the coverage diff before Phase 10.
