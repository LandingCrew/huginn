# Doc 9 implementation map: what to build, what to prune

**Status:** plan, 2026-10-08. Nothing here is built. Merged from six read-only passes over the code, one per part of the redesign (scoring and context, learner and persistence, item description, state and sensors, slots and wildcards, tooling and config), with the claims that change the plan spot-checked against the source. A fresh-context verifier then tried to invalidate it (2026-10-08); its corrections are applied.

The target is the model in [doc 9](9-context-as-learner-input.md): `score = Σ θ·need·cap + b`, a conditional logit over the page with an outside option, a diagonal-Gaussian belief per weight, the Bayesian challenger rule and uncertainty-ranked wildcards.

**Size:** roughly 7–8k lines are pruned or replaced, most of it in the classifiers (~2,600), the context rules (~1,200), the multipliers and prior (~1,000) and the per-type dumps (~950). Counts are approximate, from the passes.

Each phase lists what it builds and what it may prune. A phase only prunes what nothing later still reads.

**As built (R2, 0.23.12), where it differs from the plan above:**
- The rules live in `src/core/` (`EffectRules`, `EffectMapper`, `EffectColumns.h` generated from effects.csv, and `MiniRegex`: std::regex has no lookbehind and is slow in Debug) and are ported from the Python reference extractor that measured doc 9's coverage (`tools/effects/reference/`), not from the classifiers; `SpellClassifier`/`ItemClassifier`/`WeaponClassifier` code was not reused. The game side (`src/effect/`) only reads forms.
- The per-load-order override (layer 2) is checked **first**, before the keyword table, so an entry can correct a keyword misroute; it is an optional `Huginn_EffectOverrides.ini` (none ships yet).
- The catalog reads the forms when the main menu first opens (a main-thread task queued then), not in Huginn's kDataLoaded handler: SKSE hands kDataLoaded to plugins in turn, and keyword distributors (KID, SPID) that run after Huginn add keywords the rules read (LoreRim's `DBWR_Silver*`). A task queued from kDataLoaded is no promise of "later" (SKSE may run tasks added during its pass in the same pass). kNewGame/kPostLoadGame build too, as a fallback for a setup that skips the main menu (a no-op once built). The mapping runs on a worker thread (seconds in Debug on LoreRim).
- The cross-features are `src/core/CrossFeatures.h` + `src/effect/CrossFeatures.*` (not `src/learning/`), wired only as far as `hg cap`: nothing computes them per tick while nothing reads them. R4 is the first per-tick reader.
- Candidates do not carry a catalog index yet (it would change `CandidateTypes`, and R2 changes no scores); the catalog is keyed by FormID. Do it with R4.
- The armour items (all carried armour a candidate; the `ExternalEquipListener` armour skip) are split into their own PR: they change candidates and accept%.
- A Cloak/hazard is damage itself only by a MagicDamage* keyword; otherwise it maps through its payload spell, with no payload by its own description, and with neither it is left out of coverage like a helper.
- A graded column with magnitude 0 has an unknown strength. On a script route (keyword, name, description, override) it is the neutral value 0.5 (times D where the rule has one), never the top; presence-only columns stay 1. Through the engine's data (route Data) an unknown strength (magnitude 0; a Light with no light radius) is resolved from the effect's own text: a description that hits a no-column rule is counted unmapped ("Restoration spells are 25% more powerful"); a description that names a column keeps the row under that column, with its stated number as the magnitude, or a stated percentage as the value p/100 outside the population (Dragonhide's "ignores <80>%" is 0.8 -- percentages and points never share a population), or with no number the neutral value 0.5; a name of the same family keeps it at 0.5; a visible row with no description beside a row the item keeps is a carrier, dropped and not counted (Requiem's Dispel Armor, the Mystic/Dread variants beside Bound Armor); anything else is counted unmapped (Instant Kill, Soul Gem Evocation, Wabbajack). `huginn_effect_report --carriers-out` lists every carrier and prints coverage both ways. A Light effect grades its associated light's radius. A row of unknown strength (0.5) counts for its column only when the item has no row of known strength there, and is the item's primary row (delivery, timing, school) only when it keeps no known row. Percentages valued as p/100 on a points column (defense_armor) are an approximation that ranks them.
- Known mapping issues for the R6 data review (pre-existing, not R2 regressions; left as they are): Wind Knockup -> utility_unlock; "unlocks the seal" / "new facets" -> utility_unlock; Windwalker's immunity to knockdown -> control_stagger; the Thieves Guild Gloves' poison-resistance reduction -> resist_poison; Frostmoon Howl and Holy Aura -> damage by name; Control Weather -> influence_command; Soul Split, Power of the Master, Dark Sacrifice and Necromancer's Ritual -> summon_reanimate.
- The catalog is built once, after keyword distributors; game data changed at runtime after a save loads (a Papyrus AddKeywordToForm, SetNthEffectMagnitude, an effect a script adds) is not seen. The LoreRim gate found one such item: Waterskin.esp's "Waterskin (Full)" gains a "Restore Hunger Very Small" row after load.
- Tempering adds (h - 1) x 10 damage (the registry's measured model), it does not multiply.

- **As built (R3, 0.23.14).**
  - **The definition is the csv.** `needs.csv` gained `curve_kind`, `curve_p1`, `curve_p2` (each need's default curve, read off the prose `curve` column; where the csv gives only a centre, the slope is a designer default) and `r3_input` (the curve's input as a formula over the snapshot's fields). `tools/needs/make_need_ids.py` generates `core/NeedIds.h` and the `[Needs]` block of `configs/Huginn.ini`; `NeedIdsTests` fails on drift.   - **Drop ahead** (`state/DropAheadProbe`, `core/DropAhead.h` `ProbeAll`). Three points at 70/175/280 units along the movement (>= 20 units/s, else the facing). Each is first reached by two horizontal picks from the previous point (the player for the first), at waist (64) and knee (24) height above the PREVIOUS point's ground (the player's feet, then each reached point's down-ray hit), so the picks climb a walkable slope (round 3: from the feet alone, probe 3 went unknown above ~5 degrees). ANY hit on the waist pick blocks, whatever its layer (a wall, a door, an invisible wall or collision box at an edge, a slope steeper than ~42 degrees). A hit on the knee pick is told apart by the down ray at the point: ground there at or above the knee height is rising ground or a step up (known); lower ground or a void behind is a parapet or low wall (blocked). The first blocked point and every one beyond it are unknown. Then a ray 4000 units down from the point at waist height above the previous ground: a hit on ground (static, anim static, transparent, trees, props, terrain, ground) is the surface; actors and clutter are cast through from just past the hit, at most 8 times (`kMaxRecasts`), and running out makes that one point unknown; no hit at all is a real void (a very big drop). All unknown = -1, "not measured". The sequence is core code over an injected ray cast and host-tested (parapet, invisible wall, uphill, stairs, a crowd, which point becomes unknown, walkable slopes of 5-30 degrees, a 6-degree rise to a crest with a cliff behind, a step up). Ray filter: layer `kLOS` in the player's own collision group (its bodies never block). Water: `TESObjectCELL::GetWaterHeight` at each reached point.
  - **Where the rays run (verifier rounds 1 and 2).** Not on the update loop: it is an input-event sink on a game job thread (round 1 found every live reading "not measured" because the first version refused to cast there), and SKSE's task queue is drained on job threads too (round 1's task version ran on six different job threads; round 2 removed it). The rays are cast from a vtable hook on `PlayerCharacter::Update` (index 0xAD, installed in `SKSEPlugin_Load`), called from the game's main update -- the place prior art casts camera rays from (SkyrimCameraDisocclusion). Throttled to every 100 ms; on at kPostLoadGame / kNewGame, off at kPreLoadGame and when the main menu opens (quit to the main menu leaves the player singleton alive); skipped while a LoadingMenu is open, without player 3D, a parent cell, an attached cell or a physics world, and while airborne, swimming or mounted. The world is held by an NiPointer and read under `bhkWorld::worldLock` (BSReadLockGuard). A position jump past 500 units between two probes is a teleport: the heading comes from the facing (round 3 saw the old-to-new delta used after a coc). Anything the probe throws is caught and logged once; the game's update has already run, first. The sensor reads the last reading (older than 1 s: not measured). A test-mode run that loaded a game fails unless the probe took at least one measured reading (a plain run waits up to 10 s for it). In game the hook ran on one thread throughout (a change would log `THREAD CHANGED`); across five `coc` cell changes (`run_tests.py --coc`) it measured again in each new cell with no crash; no LoadingMenu skip was logged, because the hook never ran while a LoadingMenu was open (the loads finished between two of its calls) -- the guard stays for the case it does.
  - **Known limits, not fixed (rounds 2 and 3):** an obstacle open between the knee and the waist (a railing with a gap there) is not seen, so a void behind it reads as a cliff; the water height comes from the player's cell, so a river across a cell border can be missed; a seam or hole in the terrain mesh can read as a void; a crevasse narrower than the 105-unit probe spacing can be stepped over. Mounted is skipped (a fix must cast from the horse's feet: the player's Z is the saddle).
  - **Cadence: not the pipeline** (verifier round 1). `needs/NeedMonitor` builds the live snapshot and the vector every update tick (after the polls), logs a `[Needs]` debug line when the 0.05 signature changes (at most one a second) and feeds the Debug capture. Moving the signature into the gate is now an R8 item, with the verifier's timing model as the reason.
  - **Timers are wall clock.** steady_clock, as asked, for the combat and submerged timers, the damage sums and the sole-hostile time to kill: time in a menu counts, so combat onset can expire behind an open inventory. The user is deciding whether to pause them in menus.

### Phase 5: make the slot side sign-safe (lands before the scorer)

Log-odds scores can be zero or negative; the slot code assumes positive ratios.

- **Bridge:** feed `score = ln(utility)` with σ = 0 and m = 1.5. This reproduces today's behaviour exactly, so the slot code can change first.
- **Fix every positive-score assumption:** the slot class cap (`SlotClassCap`, the need cap before R0) multiplies (helps a negative score) at `SlotAllocator.cpp:1162-1165,1844,1850`, and `DropSkipsSince(itemScore*factor)` at `SlotAllocator.cpp:1219` with its threshold comparison at `SlotClassCap.cpp:111` → an additive `k·ln d`; ratio logs at `SlotAllocator.cpp:1171,1175`, `SlotLocker.cpp:273`; `-1` as "incumbent gone" at `SlotLocker.cpp:244`, `SoakMetrics.h:141-143`; `utility = 0` for remembered-only rows at `PipelineCoordinator.cpp:366-369`; the `kOverrideUtility = 1000` sentinel (overflows under `exp`); the 0–15 widget bar; the unused "confidence" payload (`SlotUtils.h:66`).
- **Full sort:** only the top 10 are sorted (`UtilityScorer.cpp:241-249`); with full pages, slots fill from the unsorted tail.
- Update the ratio tests at `Tests.cpp:6462-6615`.
- **As built (R7, 0.23.11).** The allocator's decision logic moved whole into `src/core/SlotAllocCore.h` (a line-by-line port over plain records, templated on the score arithmetic); `SlotAllocator` keeps the seating memory, builds the input (`src/slot/SlotSnapshot.*`) and turns the core's events into logs, telemetry and Remembrance notes. The golden test: `tests/core/SlotAllocGoldenTests.cpp`, recorded snapshots in `tests/core/fixtures/slots/`, captured by `run_tests.py --capture-slots` (the old code's by branch `r7-capture-old`). ### Phase 6: the cutover (new scorer and learner)

Order inside the phase matters:

1. **Move hard zeros to `CandidateFilters` first**: spells for others with no follower near, apparel away from a workstation, torches in daylight (`ContextWeightForCandidate.cpp:25-28,346-349,415-444`), and favorites Suppress. Otherwise apparel and torches flood the page.
2. **Turn `PotionDiscriminator`'s combat timer into the `combat_onset` sensor** (`UpdateLoop.cpp:219-225`).
3. **`ChoiceLearner`** behind the existing equip bus: sparse θ keyed by a stable (needId, effectId) hash, never by position (positional keys broke once, `StateFeatures.h:63-67`); each entry {μ, σ²}; b with prior N(0, σ_b²). The choice set is the page (everything visible, including wildcard, override and Remembrance slots) ∪ the held items off the page at a learned menu cost κ ∪ "nothing pressed". u0 depends on the situation through an outside-option effect column, θ[need, out]. Update: precision += Var_p(x), step = variance. Picks in quick succession are processed in order, each removing the chosen item from the next pick's alternatives (Plackett–Luce); the repeat window still drops re-equips. This replaces the 10 s passed-over delay. Opportunity counter on need onsets next to `PipelineStateCache::Update` (`PipelineCoordinator.cpp:545`). Battery code (`RetentionAt`, `ForgetFaded`) kept, retargeted to b. Favorites Boost becomes a battery bonus.
4. **Scorer:** v = θᵀ·need once per tick, μᵢ = cap(i)·v + bᵢ, σᵢ² under the diagonal approximation, outside option; explanation = the largest θ·need·cap term. Bootstrap θ from the Phase 4 fit.
5. **The cosave moves in here** from Phase 9 (θ must survive a load before any soak): `THTA` and `BIAS` replace `BanditSerializer`'s `BNDW` in the same change.
6. **Prune at cutover, with every consumer in the same change**, or the Debug build breaks. **Done means mechanical, not a list:** a grep over `src/` and `tools/` (code, not docs) for every pruned symbol finds nothing outside the new code, and Debug and Release build clean. ## Decisions (the user, 2026-10-08)

- [x] **"Nothing pressed" is recorded when a need expires.** One record per need episode that resets with no press, with the page at the onset. It feeds u0 and opportunity counting.
- [x] **u0 depends on the situation:** an outside-option effect column, θ[need, out], learned like any other weight. Needs that never fire keep their starting value.
- [x] **Co-picks are processed in sequence** (Plackett–Luce). The user's reading: co-picks and sequential picks covary, and processing them in order keeps that out of the update.
- [x] **The page set includes everything visible:** wildcard, override and Remembrance slots too (P5 needs the choice set as shown). This reverses today's exclusion at `EquipSubscribers.h:69`.
- [x] **The menu is a second choice set** at a learned cost κ (theory page, P11). A menu pick teaches the item picked through its need × effect pairs; κ settles at the observed reach-in rate. The favorites-always-pass rule (`UtilityScorer.cpp:98-110`) goes: menu picks carry that evidence now. Today a menu pick already trains the item's own vector (`ExternalEquipLearner.cpp:67` → `SelectionTracker::Select`); what was missing is the need and effect attribution.
- [x] **All carried armour is gear and enters the candidate pool; gear in combat is left to the learner, not a hard rule.** Mid-fight swaps (gloves of Destruction ↔ gloves of Two-Handed) are free in the engine today; they are not expected to recur often, so the data per armour item will be thin, and b and the shared θ carry it. A future swap cost becomes a feature or part of κ_move. Lift `ApparelClassifier`'s scope guard (`ApparelClassifier.h:11-17`).
- [x] **Powers stay out; a bonus only if the system works very well.** Mods use powers as a grab bag (debug tools, Weathersense, prayers for favour), players keep them on the favourites list, and their context is harder to judge than spells'. Shouts are skipped too (the user, 2026-10-08).
- [x] **Target type keeps the combat-hostile union, no line-of-sight logic.** The engine's combat state is all or nothing, the crosshair sees one actor while the player sees several in frame, and manual tagging per fight is not reasonable.
- [x] **Coverage loss is not a blocker.** Script-only spells were a back-of-the-envelope concern; unmapped items still get b. Run the coverage diff before Phase 10.
