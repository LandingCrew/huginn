## v0.7.20 - High Priority Performance Optimizations (H1-H6)

**Release Status:** Complete

Performance optimizations targeting classifier efficiency and registry accessors. Based on code review `docs/claude-subsystems-code-reviews/v0.7.x-classifiers.md`.

### H5: Fix GetHitRate Double Atomic Load (FormDataCache)

**Problem:** `GetHitRate()` loads `m_cacheHits` twice (inconsistent snapshot if values change between loads).

**Solution:** Load atomics once into local variables:
```cpp
[[nodiscard]] float GetHitRate() const noexcept {
    const uint64_t hits = m_cacheHits.load(std::memory_order_relaxed);
    const uint64_t misses = m_cacheMisses.load(std::memory_order_relaxed);
    const uint64_t total = hits + misses;
    return total > 0 ? (static_cast<float>(hits) / static_cast<float>(total)) * 100.0f : 0.0f;
}
```

- **Impact:** Consistent cache hit rate calculations, correct memory ordering

### H1+H6: ScrollClassifier Delegate to SpellClassifier

**Problem:** `GetPrimaryMagnitude()` and `GetPrimaryDuration()` in ScrollClassifier duplicate the same effect cost calculation as SpellClassifier (~80 lines of duplicate code).

**Solution:** Move `GetCostliestEffect()` to public in SpellClassifier.h, delegate from ScrollClassifier:
```cpp
float ScrollClassifier::GetPrimaryMagnitude(RE::ScrollItem* scroll) const {
    if (!scroll) return 0.0f;
    auto* effect = m_spellClassifier.GetCostliestEffect(scroll);  // ScrollItem IS-A SpellItem
    return effect ? effect->effectItem.magnitude : 0.0f;
}
```

- **Impact:** Single source of truth for cost formula, ~80 lines → ~12 lines

### H2: ItemClassifier Keyword Optimization

**Problem:** `HasKeyword()` iterates all keywords per check (O(n) × 14 checks = O(14n) per item).

**Solution:** Added `BuildKeywordSet()` helper:
```cpp
std::unordered_set<std::string_view> BuildKeywordSet(const RE::BGSKeywordForm* keywordForm);
```

Refactored `ClassifySoulGem()` and `DetermineItemTags()` to use O(1) set lookups:
```cpp
auto keywords = BuildKeywordSet(keywordForm);
if (keywords.contains("SoulGemBlack")) data.magnitude = 6.0f;
```

- **Impact:** O(14n) → O(n + 14) keyword iterations per item

### H4: Registry Partial Sort Optimization

**Problem:** Registry accessors use `std::sort` (O(n log n)) for top-K queries that only need top 3 results.

**Solution:** Added `topK` parameter (default 3) and use `std::partial_sort` when k < n:
```cpp
std::vector<const InventoryItem*> GetHealthPotionsByMagnitude(size_t topK = 3) const;

// Implementation:
const size_t k = (topK > 0) ? std::min(topK, result.size()) : result.size();
if (k > 0 && k < result.size()) {
    std::partial_sort(result.begin(), result.begin() + k, result.end(), cmp);
    result.resize(k);
}
```

**Updated Methods:**
| Registry | Methods |
|----------|---------|
| ItemRegistry | GetHealthPotionsByMagnitude, GetMagickaPotionsByMagnitude, GetStaminaPotionsByMagnitude, GetResist*Potions (5), GetFortifySkillPotions, GetInvisibilityPotions, GetWaterbreathingPotions, GetSoulGems, GetSoulGemsByCapacity |
| ScrollRegistry | GetDamageScrolls, GetHealingScrolls, GetDefensiveScrolls, GetFireScrolls, GetFrostScrolls, GetShockScrolls |
| WeaponRegistry | GetFireStaffs, GetFrostStaffs, GetShockStaffs, GetArrows, GetBolts, GetSilverAmmo |

- **Impact:** O(n log n) → O(n log k) for typical top-3 queries

### H3: FormDataCache Pre-compiled Batch Statements

**Problem:** `GetBatch()` dynamically builds SQL strings and calls `sqlite3_prepare_v2()` on every invocation.

**Solution:** Pre-compile batch statements with fixed placeholder counts (10/50/100):
```cpp
enum class StmtIndex : size_t {
    // ... existing statements ...
    GetBatch10,   // 10-placeholder batch query
    GetBatch50,   // 50-placeholder batch query
    GetBatch100,  // 100-placeholder batch query
    COUNT
};
```

`GetBatch()` now selects appropriate pre-compiled statement and pads unused slots with -1:
```cpp
if (remaining <= BATCH_10) {
    batchStmt = m_stmts[static_cast<size_t>(StmtIndex::GetBatch10)];
    stmtCapacity = BATCH_10;
} // ... etc
```

- **Impact:** Eliminates dynamic SQL building and prepare() calls on hot paths

## v0.7.19 - SKSE API Call Optimizations

**Release Status:** Complete

Performance optimizations targeting redundant SKSE API calls on hot paths (100ms-500ms update cycles). Based on code review `docs/claude-subsystems-code-reviews/v0.7.x-skse-interfaces.md`.

### S3: EquippedWeapons Struct (WeaponRegistry)

**Problem:** `GetEquippedObject()` called twice per hand due to ternary pattern.

**Solution:** Added `EquippedWeapons` struct with static `Query()` factory method:
```cpp
struct EquippedWeapons {
    RE::TESObjectWEAP* rightHand = nullptr;
    RE::TESObjectWEAP* leftHand = nullptr;
    [[nodiscard]] static EquippedWeapons Query(RE::PlayerCharacter* player);
    [[nodiscard]] bool IsEquipped(const RE::TESObjectWEAP* weapon) const noexcept;
};
```

- Added overloaded `RefreshCharges(const EquippedWeapons&)` and `ReconcileWeapons(const EquippedWeapons&)`
- Original no-arg methods delegate to overloads (backward compatible)
- **Impact:** 50% fewer SKSE API calls on 100ms hot path

### S1: Combined Inventory Scan (ItemRegistry)

**Problem:** `ScanPlayerInventory()` and `ScanPlayerSoulGems()` both iterate `entryList` separately.

**Solution:** Implemented `ScanPlayerInventoryAll()` returning combined result:
```cpp
struct InventoryScanResult {
    std::vector<ScannedAlchemyItem> alchemyItems;
    std::vector<ScannedSoulGem> soulGems;
};
```

- Single traversal handles both AlchemyItem and TESSoulGem types
- Updated `RefreshCounts()`, `ReconcileItems()`, and `RebuildRegistry()` call sites
- **Impact:** 50% reduction in inventory iteration on 500ms hot path

### S5: FormID Caching in Scan Structs (ItemRegistry)

**Problem:** `GetFormID()` called repeatedly during lookup map construction.

**Solution:** Capture FormID once during initial scan:
```cpp
struct ScannedAlchemyItem {
    RE::AlchemyItem* item;
    RE::FormID formID;  // Captured once during scan
    int32_t count;
};
```

- Call sites now use `scanned.formID` instead of `item->GetFormID()`
- **Impact:** Eliminates redundant FormID lookups during reconciliation

### S2: Player Pointer Propagation (All Registries)

**Problem:** Each registry calls `RE::PlayerCharacter::GetSingleton()` independently.

**Solution:** Added overloaded methods accepting pre-fetched player pointer:
- `SpellRegistry::ReconcileSpells(RE::PlayerCharacter*)`
- `SpellRegistry::RefreshFavorites(RE::PlayerCharacter*)`
- `ItemRegistry::RefreshCounts(RE::PlayerCharacter*)`
- `ItemRegistry::ReconcileItems(RE::PlayerCharacter*)`
- `ScrollRegistry::RefreshCounts(RE::PlayerCharacter*)`
- `ScrollRegistry::ReconcileScrolls(RE::PlayerCharacter*)`

Main.cpp now queries player once and passes to all registries:
```cpp
auto* player = RE::PlayerCharacter::GetSingleton();
if (!player) return;
g_spellRegistry->ReconcileSpells(player);
g_itemRegistry->RefreshCounts(player);
// ... etc
```

- **Impact:** Single `GetSingleton()` call per update cycle instead of 6+

### S4: GetCostliestEffect Caching (SpellClassifier)

**Problem:** `GetCostliestEffect()` called 4+ times per spell during classification.

**Solution:** Compute once in `ClassifySpell()`, pass to helper methods:
```cpp
RE::Effect* costliestEffect = GetCostliestEffect(spell);
RE::EffectSetting* primaryEffect = costliestEffect ? costliestEffect->baseEffect : nullptr;
data.type = DetermineSpellType(spell, primaryEffect);
data.school = DetermineMagicSchool(costliestEffect);
data.element = DetermineElementType(costliestEffect);
```

- Updated method signatures to accept pre-computed values
- **Impact:** O(4n) → O(n) effect iterations per spell at load time

### S10: RTTI Cast Caching (WeaponRegistry)

**Problem:** `As<TESEnchantableForm>()` RTTI cast repeated multiple times in `ExtractWeaponMetadata()`.

**Solution:** Cache cast result at function entry:
```cpp
auto* enchantable = weapon->As<RE::TESEnchantableForm>();
const bool hasEnchantment = enchantable && enchantable->formEnchanting;
```

- Subsequent checks use cached `enchantable` pointer
- **Impact:** Single RTTI lookup per weapon instead of 3+

## v0.7.0 - Foundation: Classification Cache (SQLite)

**Release Status:** Complete

### SQLite Integration
- Added sqlite3 dependency via vcpkg
- Implemented `FormDataCache` class for persistent classification storage
  - See `docs/architecture/persistence.md` for implementation details

### Cache Features
- **Mod list hash invalidation**: Cache automatically invalidates when mod list changes
- **Batch insert with transactions**: Optimized bulk classification storage for performance
- **Version-aware caching**: Classifications are re-computed when classifier version changes

### Architecture
The cache sits between the Spell Registry and the classifier, preventing redundant classification work across game sessions:

```
SpellRegistry → FormDataCache (SQLite) → SpellClassifier
                     ↓
              Persistent storage
```
